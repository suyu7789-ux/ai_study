## 操作步骤

### Step 1 · 选厂商 + 申请 API Key
- **做了什么**：在 https://platform.deepseek.com/ 用手机号注册，左侧「API keys」→「创建 API key」，命名 `ai_study`，拿到形如 `sk-xxxx` 的密钥。
- **关键规矩**：Key **只显示一次**，创建后立刻复制存好（≈ Week 1 存 GitHub PAT 的规矩）。
- **知识点 / 对照 Java**：
  - API Key = 第三方接口的凭证 = **数据库密码级别的机密**，绝不截图/发群/进 git。
  - GitHub 上有机器人专门扫 `sk-` 开头的字符串盗刷，泄露 = 真金白银损失。
  - 应急流程：一旦泄露 → 立即到控制台**吊销(删除)旧 Key + 重建**。
- **坑 / 提醒**：本次学习为图方便把 key 发到了对话里，属"演示性泄露"。生产环境必须走"泄露即吊销重建"流程，把它变成肌肉记忆。

### Step 2 · 把 Key 安全放进 .env（不进 git）
- **做了什么**：先让 `.gitignore` 挡住 `.env`，再建 `.env` 写入 Key，最后用 `git status` 亲眼验证 `.env` 未被追踪。
- **命令**：
  ```bash
  # ① 先让 .gitignore 忽略 .env（用 >> 追加，切勿用 > 覆盖！）
  echo "" >> .gitignore
  echo "# 环境变量文件：存 API Key 等密钥，绝不进仓库(≈ 不提交的 application-local.yml)" >> .gitignore
  echo ".env" >> .gitignore
  cat .gitignore                 # 确认末尾有 .env

  # ② 建 week2 目录 + 建 .env（全新文件，用 > 新建）
  mkdir week2
  echo "DEEPSEEK_API_KEY=sk-xxxxxxxx" > .env
  cat .env                       # 确认是"键=值"一整行，别漏了键名

  # ③ 关键验证：git 追不到 .env
  git status                     # 输出里看不到 .env = 隔离成功
  ```
- **知识点 / 对照 Java**：
  - `.env` ≈ **不提交的 `application-local.yml` / `.properties`**：格式就是 `键=值`，等号两边不加空格、值不加引号。
  - `.gitignore` 挡住 `.env` ≈ 挡住 `target/`：`git status` 从此看不到它。
  - 密钥走**环境变量/外部配置**，绝不硬编码进代码提交（≈ 不把 `spring.datasource.password=真密码` 提交上去）。
- **坑**：
  - `>>`(追加) vs `>`(覆盖) 要分清：改 `.gitignore` 用 `>>`（否则冲掉原内容），建全新 `.env` 用 `>`。—— Week 1 `>DS_Store` 那个坑的延续。
  - 第一次写 `.env` 漏了键名，只剩光秃秃的值 `sk-xxx`，`os.getenv("DEEPSEEK_API_KEY")` 会取到 `None`。必须是 `DEEPSEEK_API_KEY=sk-xxx` 完整一行。

  - **脱敏打印**用切片 `api_key[:6]` / `api_key[-4:]`（Week 1 学过）：密钥哪怕在自己终端也别整个打出来，防截图/日志泄露。

### Step 4 · 第一次调用大模型（requests 裸调）
- **产出文件**：`week2/02_first_call.py`
- **做了什么**：用 Week 1 学的 `requests.post` 直接调 DeepSeek 的 chat 接口，看清"调大模型 = 一个 HTTP POST"的本质。
- **代码**：
  ```python
  import os
  import requests
  from dotenv import load_dotenv

  load_dotenv()
  api_key = os.getenv("DEEPSEEK_API_KEY")

  # ① 接口地址：DeepSeek chat 接口（OpenAI 兼容风格）
  url = "https://api.deepseek.com/chat/completions"

  # ② 请求头：Key 放 Authorization，格式固定 "Bearer <key>"
  headers = {
      "Authorization": f"Bearer {api_key}",
      "Content-Type": "application/json",
  }

  # ③ 请求体：模型 + 对话内容
  payload = {
      "model": "deepseek-v4-flash",
      "messages": [
          {"role": "user", "content": "用一句话解释什么是 API，面向 Java 后端开发者"}
      ],
  }

  # ④ 发 POST（json=payload 自动序列化成 JSON，≈ Jackson 序列化）
  resp = requests.post(url, headers=headers, json=payload)

  # ⑤ 状态码
  print("状态码:", resp.status_code)

  data = resp.json()

  # ⑥ 从嵌套结构挖出"模型说的话"
  #    ≈ Java: response.getChoices().get(0).getMessage().getContent()
  answer = data["choices"][0]["message"]["content"]
  print("\n🤖 模型回答：", answer)

  # ⑦ token 消耗（钱）
  cost = data["usage"]
  print(f"token 消耗：输入 {cost['prompt_tokens']} + 输出 {cost['completion_tokens']} = 共 {cost['total_tokens']}")
  ```
- **运行 & 结果**：
  ```
  状态码: 200
  🤖 模型回答： API（应用程序编程接口）是一组定义好的调用契约，允许不同模块或服务之间通过请求-响应方式进行通信……
  token 消耗：输入 15 + 输出 177 = 共 192
  ```
- **知识点 / 对照 Java**：
  - **调大模型没有魔法**：本质就是 `requests.post(url, json={...}, headers={Authorization})`，跟 Spring 里调第三方支付/短信接口一样，区别只在 body 填什么。
  - **请求 body 三要素**：`model`(用哪个模型) / `messages`(对话内容，核心) / 可选参数。
  - **`messages` 是列表**，每条 `{"role": ..., "content": ...}`：`role` 有 `system`(人设)/`user`(用户)/`assistant`(模型答)。现在只用一条 `user`。
  - **返回结构**（务必记牢）：
    - 答案在 `choices[0].message.content` ≈ `resp.getChoices().get(0).getMessage().getContent()`。`choices` 是列表(可返回多个候选)，99% 只取 `[0]`。
    - `finish_reason: "stop"` = 正常说完。
    - `reasoning_content` = DeepSeek 的"思考过程"(推理模型特性，串到 Week 3 的 CoT)，平时只用 `content`。
    - `usage` = 账单：`prompt_tokens`(输入) + `completion_tokens`(输出) = `total_tokens`。
  - **Python 取值爽点**：`data["choices"][0]["message"]["content"]` 一行链式取，因为 `resp.json()` 直接是嵌套 dict/list；Java 得先定义一堆 DTO 再 Jackson 反序列化。—— Python 做 AI 胶水层的效率优势。
- **坑**：
  - **模型名会随版本变**：一开始用旧名 `deepseek-chat` → 报 **400 invalid_request_error**，message 明确提示"支持 deepseek-v4-pro / deepseek-v4-flash"。**遇到 400 先仔细读 message，答案常在里面**。改一个字符串 `deepseek-v4-flash` 即可，其他代码不动 —— 标准化接口的威力。
  - **模型分档**：`v4-flash`(快/便宜/够用，日常首选) vs `v4-pro`(强/贵/慢，难任务才上)。学习阶段用 flash，呼应"成本控制：能用小模型别上大模型"。
  - **token 数每次浮动**：同样的问题，两次输出 token 不同(156/177)，因为模型每次生成的文字不完全一样。

### Step 5 · 换成官方 SDK（openai SDK 调 DeepSeek）
- **产出文件**：`week2/03_sdk_call.py`
- **做了什么**：把裸调换成官方 SDK，体会 SDK 封装了什么。关键：**DeepSeek 兼容 OpenAI 接口，直接用 `openai` SDK，只把 base_url 指向 DeepSeek** —— 学一次通用全行业。
- **装依赖**：
  ```bash
  uv add openai
  ```
- **代码**：
  ```python
  import os
  from openai import OpenAI          # OpenAI 官方 SDK，DeepSeek 兼容它
  from dotenv import load_dotenv

  load_dotenv()

  # ① 创建客户端（≈ new 一个配好的 FeignClient / 单例 Bean）
  #    base_url 指向 DeepSeek —— "借用 OpenAI SDK 调 DeepSeek"的关键
  client = OpenAI(
      api_key=os.getenv("DEEPSEEK_API_KEY"),
      base_url="https://api.deepseek.com",
  )

  # ② 发起对话：一个方法搞定，参数就是之前 payload 的字段
  resp = client.chat.completions.create(
      model="deepseek-v4-flash",
      messages=[
          {"role": "user", "content": "用一句话解释什么是 SDK，面向 Java 后端开发者"}
      ],
  )

  # ③ 取答案：点属性，不是中括号取字典！
  answer = resp.choices[0].message.content
  print("🤖 模型回答：", answer)

  # ④ token：同样点属性
  cost = resp.usage
  print(f"💰 token：输入 {cost.prompt_tokens} + 输出 {cost.completion_tokens} = 共 {cost.total_tokens}")
  ```
- **运行 & 结果**：
  ```
  🤖 模型回答： ……（模型正常作答）
  💰 token：输入 17 + 输出 178 = 共 195
  ```
- **知识点 / 对照 Java（本步核心）**：
  - **SDK = 封装好重复劳动的客户端库** ≈ 从"自己 RestTemplate 拼 url/header/body"升级到"用官方 FeignClient / 厂商 SDK"。省掉：拼 url、拼 Bearer、`resp.json()`、层层挖数据。
  - **⭐ 取值方式变了**：
    - 裸调返回是 **dict**，用【中括号+字符串】：`data["choices"][0]["message"]["content"]`
    - SDK 返回是 **对象**，用【点属性】：`resp.choices[0].message.content`
    - 本质：SDK 内部帮你把 JSON **反序列化成带类型的对象**（≈ Jackson 转 DTO），所以能点、有 IDE 补全、写错字段名会提示。裸 dict ≈ Java 的 `Map<String,Object>`（点不出来只能 get）。
  - **OpenAI 兼容生态**：这套 `openai` SDK 用法，通义/月之暗面/多数国产厂商通用，换厂商只改 `base_url` + `api_key` + `model`。
- **约定**：从此都用 SDK，裸调那次只为看清底层。

### Step 6 · 理解 token（计费单位 + 上下文窗口）
- **做了什么**：结合真实 `usage` 数字，搞懂 token 是什么、怎么算钱、和"记忆容量"的关系。
- **知识点 / 对照 Java**：
  - **token ≠ 字**：是模型切分文本的最小单位（tokenizer 分词），介于字符和单词之间。英文 1 token ≈ 0.75 词 ≈ 4 字符；中文 1 汉字 ≈ 1~2 token（更耗）。模型不认识文字，只认 token 对应的**数字 ID**（输入先被转成一串数字）。≈ 模型内部的"编码单元"。
  - **输入/输出分开计费，且输出更贵**（生成更耗算力）。`prompt_tokens`(输入) + `completion_tokens`(输出) = `total_tokens`。
  - **量级**：DeepSeek 每百万 token 几块钱级。单次练习调用不到 1 厘钱，整个 Week 2 几分钱 → 放心练。但**生产规模化** = 真金白银，故路线强调"成本控制/能用小模型别上大/prompt 别太长"。
  - **⭐⭐ 上下文窗口(context window)** = 单次调用能处理的 token 上限 = 模型的"记忆容量"。`输入(system+历史+本次) + 输出 ≤ 窗口上限`。≈ 固定大小的缓冲区/栈容量，装不下就截断/报错。
  - **⭐⭐⭐ 模型是无状态的**（≈ Spring 接口默认无状态、不存 session）：它**不会自己记得**上一句！多轮对话的"记忆"靠**你每轮把完整历史重新塞进 `messages` 一起发过去**。→ 对话越长 messages 越大、token 越多，直到逼近窗口上限。这是下一步产出物的核心机制。

### Step 7 · 产出物·上半：多轮对话（记住上下文）
- **产出文件**：`week2/04_chat.py`
- **做了什么**：用 `while True` 循环 + `messages` 列表做一个能记住上下文的命令行对话程序。
- **程序结构**（≈ 手动维护一个 `List<Message>` 会话缓冲区）：
  ```
  维护 messages 列表（开头放一条 system 设人设）
  循环：读输入 → append(user) → 把【整个 messages】发给模型 → append(assistant) → 打印
  ```
- **代码**：
  ```python
  import os
  from openai import OpenAI
  from dotenv import load_dotenv

  load_dotenv()
  client = OpenAI(api_key=os.getenv("DEEPSEEK_API_KEY"), base_url="https://api.deepseek.com")

  # system 只在开头放一次，给 AI 定人设/规则
  messages = [
      {"role": "system", "content": "你是一个专为 Java 后端工程师服务的 AI 助教，回答简洁，善用 Java 类比。"}
  ]
  print("🤖 多轮对话已开始（输入 exit 退出）\n")

  while True:
      user_input = input("你: ")
      if user_input.strip().lower() == "exit":
          print("再见！"); break
      messages.append({"role": "user", "content": user_input})   # 用户这句进历史
      resp = client.chat.completions.create(model="deepseek-v4-flash", messages=messages)
      answer = resp.choices[0].message.content
      messages.append({"role": "assistant", "content": answer})   # ⭐模型回复也要存回，否则下轮失忆
      print("🤖:", answer, "\n")
  ```
- **测试记忆**：先说"我叫 suyu"，再问"你记得我叫什么吗" → 模型答出"suyu" ✅ = 记忆生效。
- **知识点 / 对照 Java**：
  - **记忆的本质**：模型无状态，靠每轮把**含它上一句在内的整个 messages 重新喂过去**实现"记忆"。关键是 append(assistant) 那步，漏了下轮就失忆。
  - **`while True` + `break`** ≈ Java `while(true){...break;}`；**`input()`** ≈ `Scanner.nextLine()`(阻塞等回车)。
  - **`system` 角色**：给 AI 定人设/规则，只在开头放一次（Week 3 Prompt Engineering 的核心，先埋种子）。
  - **成本认知**：对话每多一轮，messages 越长、发出去的 token 越多（要把前面所有轮重发），越逼近上下文窗口 —— Part B 的理论在此真实发生。
- **坑**：`base_url` 把 `deepseek` 拼成 `deepseese` → 连不存在的域名，报一大串 `httpx/httpcore/start_tls` 栈。**读报错栈技巧**：别看中间 SDK 内部调用，**看最底下的真正原因**（≈ Java 的 `Caused by:`）；连接失败 90% 是地址写错/网络。动态语言字符串写错只在运行时炸（≈ Week 1 `request` 少个 s）。

### Step 8 · 产出物·下半：流式输出（stream）🎯 Week 2 完成态
- **产出文件**：`week2/05_chat_stream.py`
- **做了什么**：在多轮对话基础上加 `stream=True`，让回答像打字机逐字吐出，而非整段卡出。
- **代码**（只列与 04 的差异部分）：
  ```python
      # ① 开启流式：返回的不再是完整结果，而是"数据块迭代器"
      stream = client.chat.completions.create(
          model="deepseek-v4-flash",
          messages=messages,
          stream=True,
      )
      print("🤖: ", end="", flush=True)   # end="" 不换行，让后面的字接着打印

      full_answer = ""                     # 碎片拼完整答案（还要存回 messages 当记忆）
      # ② for 逐块接收（≈ 订阅 Flux 一块块处理）
      for chunk in stream:
          delta = chunk.choices[0].delta.content   # 每块是"增量"，只有新吐的一小段
          if delta:                                 # 有内容才处理（末块可能为空）
              print(delta, end="", flush=True)      # 实时打印，不换行
              full_answer += delta                  # 同时拼进完整答案
      print("\n")
      messages.append({"role": "assistant", "content": full_answer})   # 记忆机制不变
  ```
- **运行 & 结果**：回答**逐字冒出来**（非一次性蹦出），且多轮记忆依旧生效（答出"你是 Suyu"）。✅
- **知识点 / 对照 Java（本步核心）**：
  - **流式 = SSE**：非流式 ≈ 普通 `@RestController` 返回整个对象；流式 ≈ **SSE / `SseEmitter` / WebFlux `Flux<String>`**，服务端分块持续 push。
  - **`stream=True` 改变返回类型**：从完整 `response` 对象 → 变成**可迭代的流**，用 `for chunk in stream` 逐块取（≈ 返回值从 `ChatResponse` 变 `Flux<Chunk>`）。
  - **`delta`(增量) vs `message`(完整)**：非流式答案在 `choices[0].message.content`(完整)；流式每块在 `choices[0].delta.content`(**只有新吐的一小段**)，得自己 `+=` 拼起来才是完整答案。
  - **`flush=True` 是关键**：`print` 默认有缓冲，流式必须强制立刻刷屏，否则仍是"卡一下整段出现"，流式白做（≈ Java 的输出流 `flush()`）。

### Step 9 · temperature 实验（附：一个关于"可复现性"的重要真相）
- **产出文件**：`week2/06_temperature.py`
- **做了什么**：同一问题"用一句话形容 Java 程序员的一天"，用 `temperature=0` 和 `temperature=1.3` 各问 3 次，对比输出差异。
- **代码**：
  ```python
  question = "用一句话形容 Java 程序员的一天"

  def ask(temperature: float) -> str:
      resp = client.chat.completions.create(
          model="deepseek-v4-flash",
          messages=[{"role": "user", "content": question}],
          temperature=temperature,      # ← 实验主角
      )
      return resp.choices[0].message.content

  for i in range(3): print(f"第{i+1}次: {ask(0)}")     # 稳定组
  for i in range(3): print(f"第{i+1}次: {ask(1.3)}")   # 发散组
  ```
- **知识点 / 对照 Java**：
  - **temperature = 随机性旋钮**：模型生成每个字是在候选词里按概率挑，temperature 控制挑得多保守/多大胆。
    - `0` → 每步倾向选概率最高的词 → 更稳定、更可复现（提取/分类/要JSON/算账，**业务首选**）。≈ 想要一个确定性函数，好测试好排查。
    - `1` 左右 → 适度随机有创造性（日常对话/文案）。
    - `1.3+` → 放飞发散甚至胡言（头脑风暴/写诗）。
- **⚠️ 关键坑 / 真相（本步最值钱的一课）**：
  - **实验现象**：`temperature=0` 三次输出**并非完全相同**，只是风格更收敛；`1.3` 三次明显各不相同、用词更花。趋势对，但没到"逐字复制"。
  - **原因**：真实 LLM API 上 `temperature=0` **不保证 100% 可复现**——① V4 多为 MoE(混合专家)架构，每次可能路由到不同专家；② GPU 并行+浮点+批处理，请求跟谁拼一批都影响浮点结果，滚雪球到选词。所以它是"贪心采样/更稳定"，不是"确定性函数"。
  - **⭐工程认知(面试加分)**：**不要依赖 LLM 输出完全可复现**，即使 temp=0 也要假设它可能变。→ Week 3 做"简历→固定JSON"时，光调低 temperature 不够，还要**用代码校验结构(Pydantic 解析、字段缺失就重试)兜底**。这就是路线的"幻觉治理/结果可验证"。
  - **对照 Java**：像调第三方接口，哪怕文档写"幂等"，生产代码仍加重试+校验+兜底——不敢 100% 信外部系统。对 LLM 更要如此。
