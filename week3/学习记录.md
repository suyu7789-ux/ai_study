### Step 1 · System Prompt 角色设定（承接 Week 2 埋的种子①）

- **做了什么**：同一个问题「什么是多态？」，用 3 种不同的 `system` 人设去问，直观看到人设从根上决定模型的身份、语气、行为边界、输出格式。
- **产出文件**：`week3/01_system_prompt.py`
- **我敲的完整代码**：

  ```python
  import os
  from openai import OpenAI
  from dotenv import load_dotenv

  load_dotenv()
  client = OpenAI(api_key=os.getenv("DEEPSEEK_API_KEY"), base_url="https://api.deepseek.com")

  # 同一个问题，用 3 种不同的 system 人设去问，看行为怎么变
  question = "什么是多态？"

  def ask(system_prompt: str) -> str:
      resp = client.chat.completions.create(
          model="deepseek-v4-flash",
          messages=[
              {"role": "system", "content": system_prompt},   # ← 人设放这里
              {"role": "user", "content": question},
          ],
      )
      return resp.choices[0].message.content

  # 人设 A：严厉的技术面试官
  print("===== 人设A：严厉面试官 =====")
  print(ask("你是一位严厉的大厂技术面试官，只用一句话犀利地反问考察对方，不准直接给答案。"))

  # 人设 B：耐心的少儿编程老师
  print("\n===== 人设B：少儿编程老师 =====")
  print(ask("你是教小学生的编程老师，必须用生活中的比喻解释，禁止出现任何专业术语和代码。"))

  # 人设 C：只讲 Java 的严谨助教（限定回答格式）
  print("\n===== 人设C：Java助教（限定格式）=====")
  print(ask("你是 Java 技术助教。只准回答与 Java 相关的内容，回答控制在 3 行以内，必须给一个 Java 代码例子。"))
  ```
- **运行 & 结果**：

  ```java

- **知识点 / 对照 Java**：

  - **`system` = 全局策略 / 行为准则**，不处理具体某个请求，但框定所有请求的处理方式（语气、边界、格式、能答什么不能答什么）。≈ Spring 的 `@ControllerAdvice` / 全局拦截器 + 一份《接口规范文档》；也像给 Service 注入的全局 Strategy 配置。
  - **`system` 与 `user` 的分工**：`user` 是每次请求的入参，`system` 是"Bean 启动时"就定好的准则。模型对 `system` 的服从优先级高于 `user`，所以**规则/格式/安全边界要写进 `system`**，别每次拼在用户问题里。
  - **三个人设验证了 `system` 能控制三种东西**：A=行为边界（只反问不给答案）、B=表达约束（禁术语）、C=**输出格式**（3 行 + 必给代码）——C 证明了 `system` 能约束"输出结构"，这是通往 Step 4「结构化 JSON 输出」的桥。
- **坑 / 关键伏笔**：

  - 人设 C 说"3 行以内"，实际算上代码块输出了约 4 行——**自然语言约束是"软约束"，模型不保证 100% 遵守**。
  - → 结论：到 Step 4 要机器解析 JSON 时，光靠 `system` 说"请返回 JSON"不够，必须**用代码校验结构 + 缺字段就重试**兜底（承接 Week 2 种子②：别 100% 信 LLM 输出）。

### Step 2 · Few-shot（给示例提升准确率）

- **做了什么**：同一个情感分类任务（输出 `情感|强度(1-5)`），对比 Zero-shot（只描述规则）和 Few-shot（用"伪造历史对话"塞 3 个范例）的输出差异。
- **产出文件**：`week3/02_few_shot.py`
- **我敲的完整代码**：
  ```python
  import os
  from openai import OpenAI
  from dotenv import load_dotenv

  load_dotenv()
  client = OpenAI(api_key=os.getenv("DEEPSEEK_API_KEY"), base_url="https://api.deepseek.com")

  # ===== 方式一：Zero-shot（不给例子，只描述）=====
  print("===== Zero-shot：不给例子 =====")
  resp = client.chat.completions.create(
      model="deepseek-v4-flash",
      messages=[
          {"role": "system", "content": "判断用户这句话的情感，输出格式：情感|强度(1-5)"},
          {"role": "user", "content": "这框架文档写得跟天书一样"},
      ],
  )
  print(resp.choices[0].message.content)

  # ===== 方式二：Few-shot（用假的历史对话塞 3 个范例）=====
  print("\n===== Few-shot：给 3 个范例 =====")
  resp = client.chat.completions.create(
      model="deepseek-v4-flash",
      messages=[
          {"role": "system", "content": "判断用户这句话的情感，输出格式：情感|强度(1-5)"},
          # —— 下面这 6 条是"伪造的历史"，教模型照着答 ——
          {"role": "user", "content": "今天代码一次就跑通了"},
          {"role": "assistant", "content": "正面|4"},
          {"role": "user", "content": "又加班到十点"},
          {"role": "assistant", "content": "负面|3"},
          {"role": "user", "content": "项目终于上线了"},
          {"role": "assistant", "content": "正面|5"},
          # —— 真正要问的新问题 ——
          {"role": "user", "content": "这框架文档写得跟天书一样"},
      ],
  )
  print(resp.choices[0].message.content)
  ```
- **运行 & 结果**：
  ```
  ===== Zero-shot：不给例子 =====
  负面|4

  ===== Few-shot：给 3 个范例 =====
  负面|3
  ```
- **知识点 / 对照 Java**：
  - **术语**：Zero-shot=不给例子直接问；Few-shot=先给几个"输入→输出"范例再问；shot=示范一次。
  - **实现手法**：用 `messages` **伪造几轮历史对话**（user/assistant 交替），假装模型已成功答过几次，它就会延续同样格式答新问题。
  - **Few-shot ≈ 给下游同事的"请求/响应示例"**、参数化测试用例：不啰嗦讲规则，给几组标准样例，对方照着来。范例质量决定输出质量（要覆盖典型情况 + 格式绝对统一）。
  - **本次实验的真实结论（比预期更有意思）**：
    - Zero-shot 也输出了干净的 `负面|4` —— 任务简单 + 指令清晰 + 模型强时，**Zero-shot 就够了**，Few-shot 并非必须。
    - 差异在强度分 4 vs 3：Zero-shot 的打分是自由心证；Few-shot 用 3 个锚点（跑通=4/加班=3/上线=5）**校准了评分尺度**，模型把"文档像天书"对齐"加班到十点"量级 → 给 3。**Few-shot 不只锁格式，还能统一主观判断的尺度（calibration）**。≈ 代码评审给基准样例（"这种算3分那种算5分"），多人打分才可比。
  - **何时用 Few-shot**：格式怪异难描述 / 需要统一打分分级尺度 / 模型在某类输入上总出错（把错例的正确答案补进范例 ≈ 修 bug 补回归用例）。指令能说清的简单格式用 Zero-shot 即可。
- **坑 / 成本意识**：范例是**每次请求都要重发**的（无状态），6 条伪历史让输入 token 翻好几倍。范例数量=准确率 vs 成本的权衡，通常 3~5 个高质量范例到收益拐点。

### Step 3 · 思维链 CoT（Chain of Thought）

- **做了什么**：对比同一道容易产生歧义的算术逻辑题，不给思考空间的 Direct Answer 与显式引导“一步步思考”的 CoT 在推导路径与结论上的巨大差异。
- **产出文件**：`week3/03_cot.py`
- **我敲的完整代码**：
  ```python
  import os
  from openai import OpenAI
  from dotenv import load_dotenv

  load_dotenv()
  client = OpenAI(api_key=os.getenv("DEEPSEEK_API_KEY"), base_url="https://api.deepseek.com")

  question = """
  小明有 5 个苹果。他吃了 2 个，然后买了一箱苹果，一箱里有 12 个。
  接着他把其中一半的苹果分给了小红。
  后来小红又退还给了他 2 个苹果。
  请问小明现在手头一共有多少个苹果？
  """

  # ===== 方式一：Direct Answer（直接要结论） =====
  print("===== 方式一：Direct Answer（直接要答案） =====")
  resp = client.chat.completions.create(
      model="deepseek-v4-flash",
      messages=[
          {"role": "system", "content": "你是一个数学助手。直接输出最终的数字答案，不要包含任何解释或思考过程。"},
          {"role": "user", "content": question},
      ],
  )
  print("直接回答结果:", resp.choices[0].message.content)

  # ===== 方式二：Chain of Thought (CoT 思维链) =====
  print("\n===== 方式二：Chain of Thought (CoT 思维链) =====")
  resp = client.chat.completions.create(
      model="deepseek-v4-flash",
      messages=[
          {"role": "system", "content": "你是一个严谨的逻辑分析助手。请先一步一步详细列出推理和计算步骤，最后在最后一行单独输出答案格式：最终答案：X 个。"},
          {"role": "user", "content": question + "\n请一步步思考并计算。"},
      ],
  )
  print("思维链 CoT 输出:\n", resp.choices[0].message.content)
  ```
- **运行 & 实际结果**：
  ```text
  ===== 方式一：Direct Answer（直接要答案） =====
  直接回答结果: 9.5

  ===== 方式二：Chain of Thought (CoT 思维链) =====
  思维链 CoT 输出:
    小明最初有5个苹果，吃了2个后剩下3个。接着他买了一箱12个苹果，此时他手头共有 3+12=15个苹果。然后他把其中一半的苹果分给小红，这里“其中一半”指的是新买一箱中的一半，即12的一半是6个。分给小红后，他剩余3个原有的和6个新买的，共9个。最后小红退还给他2个，所以现在共有 9+2=11个苹果。

  最终答案：11 个。
  ```
- **知识点 / 对照 Java**：
  - **结果分析**：
    1. Direct Answer 输出了 `9.5` —— 模型没有“思考缓冲区”，直接按公式盲算 $(15/2) + 2 = 9.5$，产生了切割半个苹果的不合逻辑结论！
    2. CoT 输出了 `11` —— 模型在一步步吐出 Token 时，自发分析出了自然语言中“其中一半”指的是“新买的一箱中的一半（6个）”，避免了算错。
  - **CoT ≈ 复杂业务拆分为管道/中间 Trace 日志**：LLM 是自回归的，前面吐出的每个中间 Token 都会变成后续推导的 Prompt 上下文。显式开启思维链，相当于给 LLM 提供了“草稿纸”，大幅减少跳跃导致的逻辑与计算 Bug。

### Step 4 · 结构化 JSON 输出与 Pydantic 强类型校验

- **做了什么**：结合 API 的 `response_format={"type": "json_object"}` 参数与 System Prompt 约束，让大模型稳定输出纯 JSON 字符串，并使用 `pydantic` 进行强类型校验与反序列化。
- **产出文件**：`week3/04_json_output.py`
- **我敲的完整代码**：
  ```python
  import os
  import json
  from openai import OpenAI
  from dotenv import load_dotenv
  from pydantic import BaseModel, Field

  load_dotenv()
  client = OpenAI(api_key=os.getenv("DEEPSEEK_API_KEY"), base_url="https://api.deepseek.com")

  # ===== 1. 定义期望的数据结构 (Pydantic Model ≈ Java DTO / Entity) =====
  class ProductReviewAnalysis(BaseModel):
      product_name: str = Field(description="被评论的产品名称")
      sentiment: str = Field(description="情感倾向：正面/负面/中立")
      score: int = Field(description="打分 1-5 分")
      summary: str = Field(description="一句话评论总结")
      tags: list[str] = Field(description="提取关键词标签")

  # 待分析的原始文本
  raw_review = """
  昨天刚收到的 SoundCore 蓝牙耳机，续航确实强，听了一整天还有电。
  但是佩戴超过 2 小时耳朵有点涨痛，降噪效果一般般，公车上的轰鸣声降不下来。
  整体对得起 299 这个价格吧，给个中评。
  """

  # ===== 2. 编写 Prompt 并启用 response_format={"type": "json_object"} =====
  prompt = f"""
  请分析以下商品评价，并输出 JSON 格式的结果。

  JSON 格式要求：
  - product_name: 字符串（产品名称）
  - sentiment: 字符串（只能是 "正面"、"负面"、"中立" 之一）
  - score: 整数（1 到 5）
  - summary: 字符串（一句话总结）
  - tags: 字符串数组（核心标签列表）

  商品评价内容：
  {raw_review}
  """

  resp = client.chat.completions.create(
      model="deepseek-v4-flash",
      response_format={"type": "json_object"},
      messages=[
          {"role": "system", "content": "你是一个严谨的数据提取助手。你必须始终返回合法的 JSON 对象。"},
          {"role": "user", "content": prompt},
      ],
  )

  json_str = resp.choices[0].message.content

  # ===== 3. 解析与 Pydantic 校验 (≈ Java Jackson 反序列化 + @Valid) =====
  raw_data = json.loads(json_str)
  review_obj = ProductReviewAnalysis(**raw_data)
  print(f"产品名称: {review_obj.product_name}")
  print(f"情感倾向: {review_obj.sentiment}")
  print(f"评分: {review_obj.score} / 5")
  print(f"总结: {review_obj.summary}")
  print(f"标签: {review_obj.tags}")
  ```
- **运行 & 实际结果**：jiejie sho
  ```text
  ===== 发送结构化 JSON 请求 =====
  模型返回的原始 JSON 字符串:
   {
    "product_name": "SoundCore蓝牙耳机",
    "sentiment": "中立",
    "score": 3,
    "summary": "续航强但佩戴不适和降噪一般，整体对得起价格。",
    "tags": ["续航强", "佩戴不适", "降噪一般", "性价比好"]
  }

  ===== 3. Pydantic 强类型校验与对象转换 =====
  ✅ Pydantic 校验通过！提取的数据对象如下：
  产品名称: SoundCore蓝牙耳机
  情感倾向: 中立
  评分: 3 / 5
  总结: 续航强但佩戴不适和降噪一般，整体对得起价格。
  标签: ['续航强', '佩戴不适', '降噪一般', '性价比好']
  ```
- **知识点 / 对照 Java**：
  - **后端必会模式**：自然语言输入 → Prompt 控制逻辑 → `response_format={"type": "json_object"}` 强制语法 → `Pydantic` 强类型 DTO 反序列化与校验。
  - **`Pydantic Model` ≈ Java DTO / Entity 对象 + `@Valid` 校验**。
  - `response_format={"type": "json_object"}` 从 API 层面杜绝了模型返回 Markdown 围栏（如 ``json ... ``）带来的 `json.loads` 字符截断问题。

### Step 5 · 防幻觉（"不确定就说不知道" + "只根据给定资料回答"）

- **做了什么**：给同一份"公司规章制度"资料，问两类问题——① 资料里有明确答案的、② 资料里完全没提的。对比"普通 Prompt"和"防幻觉强约束 Prompt"，验证**用 System 边界约束把模型从"凭记忆答"逼成"基于资料答 + 该拒答就拒答"**。这正是全程贯穿的第 1 条关键认知（幻觉治理）在 Prompt 层的落地。
- **产出文件**：`week3/05_anti_hallucination.py`
- **核心代码（防幻觉 System Prompt 是关键）**：
  ```python
  # 强约束：划死边界 + 给标准拒答话术
  strict_system_prompt = """
  你是一个严格防幻觉的知识库问答助手。请遵守以下原则：
  1. 必须【仅】根据【参考资料】中明确提及的内容进行回答。
  2. 严禁使用你自身的知识库进行推测、延伸或补充臆断。
  3. 如果【参考资料】中未包含回答问题所需的直接信息，你必须明确回答："抱歉，给出的参考资料中未提及该信息。"
  4. 引用资料回答时，保持事实准确，不夸大不篡改。
  """
  # 把"资料 + 问题"一起塞进 user，让模型只在资料范围内作答
  messages=[
      {"role": "system", "content": strict_system_prompt},
      {"role": "user", "content": f"参考资料：\n{context_doc}\n\n问题：{q}"},
  ]
  ```
- **运行 & 实际结果**：
  ```text
  ===== 实验一：普通 Prompt（未做防幻觉约束） =====
  针对未提及问题的回答 (普通Prompt):
   根据您提供的资料，目前没有关于年终奖发放月数和餐补标准的信息。建议您咨询人事部门或查阅员工手册。

  ===== 实验二：防幻觉强约束 Prompt（边界清晰 + 拒答机制） =====
  1. 资料中有答案的问题回答:
   根据参考资料，单笔 600 元的打车费超过 500 元，需 VP 审批。

  2. 资料中无答案的问题回答 (成功防幻觉/正确拒答):
   抱歉，给出的参考资料中未提及该信息。
  ```
- **知识点 / 对照 Java**：
  - **防幻觉的两把锁**：① **收窄知识来源**——"只准用参考资料，禁用你自己的知识库"，把开放问答改造成"闭卷→开卷"；② **给定拒答出口**——明确告诉模型"没有就照这句话拒答"，否则模型天然倾向"编一个看起来合理的答案"填空。
  - **对有答案的问题不能误伤**：实验证明强约束下"600 元 > 500 元需 VP 审批"照样答对——防幻觉不是"什么都不敢答"，而是"有据则答、无据则拒"。
  - **≈ 后端的参数/权限校验思路**：不信任外部输入（这里是"模型的记忆"），只放行白名单内（参考资料内）的数据；命中不了就返回一个**受控的标准响应**（拒答话术），而不是抛一个不可控的脏数据出去。
  - **本次结论（超出预期）**：即便是"实验一"的普通 Prompt，DeepSeek 也没瞎编，而是老实说"资料里没有"——说明**现代强模型本身已有一定拒答倾向**；但生产上不能赌模型自觉，必须靠 System 强约束把"拒答"变成**确定性行为**（尤其换小模型/复杂资料时）。这条直接指向阶段二 RAG 的核心：**答案必须有出处、可验证**。

### Step 6 · ⭐产出：简历信息提取器（本周核心项目 · 承接 Week 2 种子②"别 100% 信 LLM"）

- **做了什么**：把 Step 1~5 全部串起来做一个**能进简历的完整小项目**——输入一段非结构化简历文本 → 输出严格结构化的 JSON → Pydantic 强类型校验 → **校验失败把错误反馈回上下文让模型自我纠正、自动重试** → 最终拿到可直接用的 Python 对象。这是"结构化输出 + 防幻觉 + 校验兜底"的综合实战。
- **产出文件**：`week3/06_resume_parser.py`
- **核心设计（重点是"重试兜底"这段工程逻辑）**：
  ```python
  # 嵌套 Pydantic 模型：ResumeData 内含 教育/工作/项目 三个子列表（≈ 多层 DTO 聚合）
  class ResumeData(BaseModel):
      name: str
      years_of_experience: int = Field(description="未提及或应届生填 0")
      skills: list[str]
      education_list: list[Education]
      work_experience_list: list[WorkExperience]
      projects: list[Project]

  def parse_resume(raw_text: str, max_retries: int = 3) -> ResumeData:
      messages = [{"role": "system", ...}, {"role": "user", ...}]
      for attempt in range(1, max_retries + 1):
          resp = client.chat.completions.create(
              model="deepseek-v4-flash",
              response_format={"type": "json_object"},   # 语法层强制 JSON
              messages=messages,
          )
          raw_json_str = resp.choices[0].message.content
          try:
              return ResumeData.model_validate_json(raw_json_str)   # 结构层强校验
          except (json.JSONDecodeError, ValidationError) as err:
              # 关键：把"上次的错误输出 + 具体报错"塞回对话，让模型下一轮自我纠正
              messages.append({"role": "assistant", "content": raw_json_str})
              messages.append({"role": "user",
                  "content": f"上次输出的 JSON 存在校验错误: {err}。请重新纠正并输出合法的 JSON 对象。"})
              if attempt == max_retries:
                  raise RuntimeError("超过最大重试次数，简历解析失败。") from err
  ```
- **运行 & 实际结果（真实触发了 3 次重试，极具说服力）**：
  ```text
  --- [Attempt 1/3] 正在调用 API 进行简历提取... ---
  ⚠️ 第 1 次解析/校验失败，错误原因: 6 validation errors for ResumeData
  name  Field required [type=missing, ...]        # ← 模型第一次用了中文键名"姓名"，导致英文字段全缺

  --- [Attempt 2/3] 正在调用 API 进行简历提取... ---
  ⚠️ 第 2 次解析/校验失败，错误原因: 4 validation errors for ResumeData
  work_experience_list.0.role  Field required     # ← 键名改对了，但嵌套子对象里 role/duration/tech_stack 又漏字段

  --- [Attempt 3/3] 正在调用 API 进行简历提取... ---
  ✅ 第 3 次尝试解析成功并验证通过！

  ========== 最终结构化结果 (Pydantic Object) ==========
  👤 姓名: 张伟
  📞 电话: None
  📧 邮箱: None
  💼 经验年限: 0 年
  🛠️ 核心技能: Java, Spring Boot, MyBatis-Plus, Spring Cloud, Python, ...

    - 浙江大学 | 本科 | 计算机科学与技术 (None)
  🏢 实习/工作经历:
    - 杭州某某科技股份有限公司 (Java 后端开发实习生, 2025.06 - 2025.12)
  🚀 项目经验:
    - 项目名称: AI 智能简历解析与问答 Agent 系统 (个人独立开发)
  ```
- **知识点 / 对照 Java**：
  - **完整链路 = 一条"带质检的数据管道"**：非结构化文本 → System/User Prompt（业务规则）→ `response_format` 强制 JSON（语法层）→ Pydantic 校验（结构层）→ 失败重试（容错层）→ 干净的对象出口。≈ Controller 收脏数据 → DTO + `@Valid` 校验 → 不过就有兜底重试，而不是让脏数据流进 Service。
  - **⭐本次最大收获——"Self-Correction 自我纠正重试"**：这就是 Week 2 埋的种子②「别 100% 信 LLM 输出」的正式兑现。真实跑下来模型**前两次都出错**（先中文键名、再嵌套字段缺失），靠"把报错原文喂回上下文"让它逐轮修正，第 3 次才成功。**证明生产级 LLM 调用必须自带校验 + 重试，不能裸信一次输出。**
  - **嵌套模型校验**：`ResumeData` 里套 `Education/WorkExperience/Project` 三层列表，Pydantic 会**递归校验到最内层字段**（报错精确到 `work_experience_list.0.role`）——和 Jackson 反序列化嵌套 DTO + 逐层 `@Valid` 一致。
  - **防幻觉在项目里的落地**：System 里写死"未提及的联系方式设为 null，未提及工作年限填 0"——结果电话/邮箱正确输出 `None`、应届生经验年限填 `0`，没有瞎编。呼应 Step 5：**宁可留空，不许臆造。**
- **坑 / 工程结论**：
  - `model_validate_json()` 比"先 `json.loads` 再 `Model(**data)`"更直接：一步完成"解析 + 校验"，且报错信息能精确定位到嵌套字段路径，方便把错误反馈给模型。
  - 重试不是"原样再问一遍"——**必须把上一次的错误输出和具体报错一起带回上下文**，模型才知道该改哪里（否则大概率重复同样的错）。这是 Self-Correction 生效的前提。
